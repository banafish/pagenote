## 一、背景与核心判断

### 判断一：外部「素材包」的真实形态是免抠图 zip

2026-08-30 调研：时光手帐 / 念念手帐 / 微手帐 / 手帐达人 / BuBu手帐等主流手账 App 的素材全部走应用内商店，**没有公开的第三方素材包文件格式，也没有官方的素材包导出**。用户之间实际流通的素材包只有两类：

1. **免抠 PNG 的 zip 压缩包**——素材站（千图网、Noooter 等）购买下载、微信群 / QQ 群分享的最主要形态。目录结构随意：根目录平铺、按主题分子文件夹、甚至 zip 套 zip；文件名编码有 UTF-8、GBK（Windows 压缩工具）、百分号编码（网页打包）三种。
2. **iPad 阵营的容器格式**——GoodNotes 元素包（`.goodnotes`）、Zinnia 素材文件（`.zinnia`），本质都是 zip 容器内嵌位图与元数据。

因此兼容策略不是「逐个 App 写适配器」（无公开格式可适配），而是**容器级兼容**：任何 zip 结构的素材文件，扫描其中可导入的位图，转换成本地自定义贴纸包。这是对 REQ-21 技术要点「扩展名就用 `.zip`」判断的镜像——竞品没有格式，容器就是通用 zip。

### 判断二：转换终点是 REQ-20 的自定义贴纸体系，不开第二条导入管线

外部包里只有位图可拿——模板版式、字体、胶带参数都是别的 App 的私有语义，映射不到拾页画布。转换产物是 `img:<sha1>` 自定义贴纸 + 素材包（`StickerPack`），预览、勾选、落库、尺寸闸全链路复用 REQ-21 既有的导入预览页，不新增任何交互与存储路径。

### 判断三：安全边界一个都不放宽

外部包同样是不可信文件（NFR-06）：路径消毒、条目数与解压体积上限、图像解码尺寸闸、内容寻址落盘全部适用。唯一放宽的是**单包原始体积**（20MB → 100MB）——免抠图 zip 本身已压缩，几十 MB 很常见；内存天花板仍由解压体积闸（64MB）守着，原始字节从不直接落盘。

## 二、需求

### REQ-29 外部素材包自动识别导入

- 参考产品：微信 / QQ「用其他应用打开」的通用文件接管、Telegram 贴纸包导入的宽容度
- 需求描述：素材包导入入口不再只认拾页格式——自动识别 zip 内容，外部素材包转换成纯贴纸包走既有导入流程；拾页分享包与备份包行为不受影响。

**验收标准**

1. **入口统一**：三个导入入口（素材页「导入素材包」按钮、Android intent / 系统分享、Windows 双击 .zip）统一走 `parsePackAuto`：拾页分享包按原格式解析（REQ-21 行为不变），备份包指路恢复入口，其余按外部包转换
2. **转换产物**：包内全部可解码图片（PNG / JPG / WebP / GIF / BMP）成为自定义贴纸素材，进入既有导入预览页逐项勾选落库（REQ-21.5～21.9 交互不变）；预览页标明「外部素材包 · 兼容其他手账应用」
3. **元数据推断**：包名取来源文件名主干（缺失时取包内唯一顶层目录名，再退「外部素材包」）；素材名取文件名主干（超长截断）；旧分组字段（category）取素材所在子文件夹名
4. **包身份稳定**：落位包的 originId 由包内全部素材内容 sha1 派生（`foreign-` 前缀），同一压缩包（或其改名副本）重复导入归位到同一个包；素材按内容寻址天然去重（REQ-20.2），包内重复图也去重
5. **可读错误（REQ-21.10 同口径）**：RAR / 7z 给出「先解压再打包成 zip」的指引；包内没有图片时说明支持的格式；拾页备份包（顶层 `entries.json`）指路「设置 → 备份与恢复」，不把备份照片误导成贴纸
6. **文件名编码还原**：GBK 打包与百分号编码的条目名还原为中文展示名；还原失败原样返回，取不出名字的按序号兜底
7. **垃圾条目与套娃**：`__MACOSX`、`.DS_Store`、`Thumbs.db`、隐藏文件等条目跳过；嵌套 zip 展开后继续扫描（最多两层）；内层路径穿越条目跳过不拒包（字节不落盘，不构成穿越风险）
8. **文件选择器**：素材页导入放行 `zip / goodnotes / zinnia` 扩展名，选择后按内容识别

**技术要点**

- 新增 `ForeignPackService`：容器魔数预检（RAR / 7z 的识别不能依赖 zip 解码失败——解析器对坏数据可能解出空包）→ 扫描图片条目（嵌套 zip 递归，解压体积预算在外层校验返回的声明体积余量内累计）→ 内容 sha1 去重 → 构造 `SharePackData`（`isForeign: true`、templates 为空）
- `SharePackService.parsePackAuto(bytes, {sourceName})` 为分流入口：`pack.json` + `app: pagenote` → 原生解析（损坏、版本过高等错误照抛）；`entries.json` → 备份指路；**别的应用恰好也叫 pack.json 的包**按 `app` 认亲字段排除后仍走外部转换；`parsePack` 严格入口原样保留，NFR-07 语义不受影响
- 文件名还原：`archive` 包对非 UTF-8 条目名退回逐字节 charCodes，latin1 形式乱码按 GBK 解码（`fast_gbk`，纯 Dart、零传递依赖）；百分号编码先解码字节再按 UTF-8 / GBK 解释；仅当条目名呈现「字符即字节」形式（全部 charCode ≤ 0xFF 且含高位）才尝试 GBK，真正的 UTF-8 中文名不会被误改
- 嵌套 zip 内层条目不再整体拒包：名字只用于展示，字节只落为贴纸，跳过即可

## 四、明确不做（Non-Goals）

- **不适配任何 App 的私有语义**（模板版式 / 字体 / 胶带参数 / 画笔）：无公开格式且持续变动，适配不可维护；外部包一律降为贴纸素材
- **不支持 RAR / 7z / tar 容器**（`archive` 依赖只含 zip）：报错指引用户自行转 zip
- **不自动生成包封面**：REQ-27.1 的既定决策（封面只来自用户上传或分享包自带 cover.png）对外部包同样成立
- **GoodNotes / Zinnia 的 plist 命名信息暂不解析**：内部结构随版本变动风险高，素材名退回位图文件名

## 五、测试与回归

`test/foreign_pack_test.dart`（19 例）：

- 转换与元数据推断：文件名主干、顶层目录兜底包名、子目录 → category、内容去重、垃圾条目过滤、嵌套 zip 与内层穿越条目
- 分流回归：拾页分享包行为不变（isForeign false）、外来 pack.json 兜底转换、备份包指路、无图包 / RAR / 7z / 损坏 zip 的可读错误
- 编码还原：GBK 乱码还原、百分号还原（含真实 zip 端到端）、正常 UTF-8 / ASCII 名不被误改
- 落库：`importFromBytes` 的 id 与解析端内容寻址一致、重复导入归位同一个包、坏图被落盘闸跳过不中断整包（NFR-06 回归）
